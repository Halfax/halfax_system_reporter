5. CONSTRAINTS AND GOTCHAS
================================================================================

[HARD RULES - NEVER VIOLATE]

1. NEVER use IoRegisterDeviceInterface for control devices
   Reason: WDM control devices (non-PnP) don't support device interfaces
   What Happens: Returns error STATUS_INVALID_DEVICE_REQUEST
   Alternative: Use IoCreateSymbolicLink only

2. NEVER use KMDF anymore
   Reason: Converted to WDM on January 24, 2026 due to KMDF framework binding failure
   History: 4+ hours of KMDF troubleshooting documented in KMDF_TROUBLESHOOTING_SUMMARY.md
   Current: WDM-only driver architecture

3. NEVER use && in PowerShell
   Reason: && is not a valid PowerShell operator (it's bash syntax)
   Alternative: Use semicolon ; to chain commands
   Example: sc.exe stop service; Copy-Item file dest; sc.exe start service

4. NEVER use PowerShell 'sc' alias
   Reason: 'sc' is an alias for Set-Content, not Service Control
   Always Use: sc.exe (with .exe extension)

5. ALWAYS sign both .sys and .cat files
   Reason: Windows Code Integrity checks both
   Order: Sign .sys first, then .cat
   Missing Either: Driver will fail signature verification

6. ALWAYS use /fd SHA256 when signing
   Reason: SHA1 is deprecated and may fail on newer Windows versions
   Error Without: "No file digest algorithm specified"

7. NEVER create WDF objects in WDM code
   Reason: WDM doesn't link WDF libraries
   What to Use: IoCreateDevice, IoCreateSymbolicLink, IoCompleteRequest

[SOFT RULES - BEST PRACTICES]

1. Copy .sys to driver package folder before building
   Reason: inf2cat.exe needs it for validation during build
   Command: Copy-Item x64\Release\halfax_telemetry_driver.sys x64\Release\halfax_telemetry_driver\

2. Update POST_REBOOT_CHECKLIST.md after major changes
   Reason: Continuity across reboots and sessions
   When: After driver changes, service changes, or architectural decisions

3. Keep REBOOT_STATUS.txt current before each reboot
   Reason: Document why reboot is needed and expected outcome
   Include: Reason, pre-reboot state, expected post-reboot state

4. Use DebugView as Administrator with "Capture Kernel" enabled
   Reason: Kernel logs require admin privileges and kernel capture
   Menu: Capture → Capture Kernel (checkbox)

5. Prefer reading large file ranges over multiple small reads
   Reason: Tool call efficiency and token usage optimization
   Example: Read 100 lines at once vs 10 reads of 10 lines

6. Quote paths with spaces in PowerShell
   Reason: Curly braces {} in paths confuse PowerShell parser
   Example: Copy-Item file "C:\Windows\System32\CatRoot\{GUID}\file"

6. ERROR PATTERNS & SOLUTIONS
================================================================================

[Error 183: "Cannot create a file when that file already exists"]
Symptom: sc.exe start halfax_telemetry fails with error 183
Cause: Symbolic link \DosDevices\HalfaxTelemetry already exists from previous driver
Root Cause: Previous driver crashed or didn't call IoDeleteSymbolicLink in Unload handler
Solution: Reboot to clean up symbolic link
Prevention: Ensure HalfaxUnload always calls IoDeleteSymbolicLink before IoDeleteDevice
Alternative: Delete and recreate service, wait 5 seconds between commands

[Error 577: "Windows cannot verify the digital signature"]
Symptom: Driver fails to load, Event Viewer shows signature verification error
Cause: Missing catalog, unsigned files, or wrong hash algorithm
Solutions:
  1. Verify catalog exists in CatRoot\{F750E6C3-38EE-11D1-85E5-00C04FC295EE}\
  2. Re-sign both .sys and .cat with /fd SHA256
  3. Verify BCD: testsigning=Yes, nointegritychecks=Yes
  4. Check Code Integrity log: Get-WinEvent -LogName 'Microsoft-Windows-CodeIntegrity/Operational'
Prevention: Always sign after deployment, sign both files, use SHA256

[ERROR 1: "Incorrect function"]
Symptom: Service starts but DriverEntry never called, no DebugView logs
Historical Cause: KMDF framework binding failure (pre-WDM conversion)
Why It Happened: KMDF loader couldn't bind to framework on this system
Resolution: Converted to WDM on January 24, 2026
Current: No longer relevant (WDM doesn't use KMDF framework)

[Build Error: inf2cat "file is missing or cannot be decompressed"]
Symptom: inf2cat.exe fails during build with error about missing .sys file
Cause: .sys file not in driver package directory when inf2cat validates INF
Solution: Copy x64\Release\halfax_telemetry_driver.sys to x64\Release\halfax_telemetry_driver\
Prevention: Add this copy step to build script or do manually before each build

[Broker Error: "No device interface found"]
Symptom: halfax_kernel_broker.exe reports "No device interface found"
Cause: Driver uses symbolic link, not device interface (WDM limitation)
Expected Behavior: Broker should fall back to \\.\HalfaxTelemetry path
Solution: This is normal for WDM control devices, broker handles fallback
Check: Verify driver is running (sc.exe query halfax_telemetry → STATE: 4)

[DebugView shows no logs]
Symptom: DebugView running but no HalfaxTelemetry logs appear
Causes:
  1. DebugView not running as Administrator
  2. "Capture Kernel" not enabled (Capture menu)
  3. Driver failed DriverEntry before logging (check Event Viewer)
  4. Wrong log filter (should not filter by process in kernel mode)
Solutions:
  1. Restart DebugView as Administrator
  2. Enable Capture → Capture Kernel
  3. Check Event Viewer: Get-WinEvent -LogName System -MaxEvents 20
  4. Clear all filters (Edit → Filter/Highlight)

8. DECISION HISTORY
================================================================================

[2026-01-24 12:00 PM - Converted KMDF to WDM]
Reason: 
  - KMDF driver failed with "Incorrect function" (ERROR 1)
  - 4+ hours of troubleshooting: signatures, catalogs, KMDF versions, exports, pnputil
  - Root cause: KMDF framework binding incompatibility on this system
  - KMDF loader failed before DriverEntry, no way to debug further

Impact:
  - Simplified architecture (no WDF dependencies)
  - Manual IRP handling instead of KMDF abstractions
  - Direct IoCreateDevice, IoCreateSymbolicLink, IoCompleteRequest
  - Removed device interface registration (control devices don't support it)

Tradeoffs:
  - More verbose code (WDM requires manual IRP processing)
  - Better control over device lifecycle
  - No black-box KMDF framework failures
  - Easier to debug (pure WDM logs, no framework layers)

Result: Driver builds successfully, ready for testing after reboot

[2026-01-23 - Used Control Device Architecture (Non-PnP)]
Reason:
  - No physical hardware device to attach to
  - Need global device accessible from any process
  - MSR/PCI/SMBus access doesn't require PnP enumeration

Impact:
  - Device created in DriverEntry, not AddDevice
  - No device interface registration (control devices don't support it)
  - Symbolic link used for user-mode access
  - Service type: kernel (not function driver)

Why This Matters:
  - IoRegisterDeviceInterface doesn't work for control devices
  - Broker must use \\.\HalfaxTelemetry path (fallback)
  - No Plug and Play events or power management

[2026-01-23 - MSR Whitelist Approach]
Reason:
  - Security: Prevent arbitrary MSR access
  - Safety: Some MSRs can brick systems or cause instability
  - Compliance: Principle of least privilege

Impact:
  - Only 11 safe read-only MSRs allowed
  - All write attempts return ACCESS_DENIED (by design)
  - Future: Add separate write whitelist if needed

Whitelisted MSRs:
  - 0xCE: MSR_IA32_PLATFORM_INFO (base frequency, max turbo)
  - 0x19C: MSR_IA32_THERM_STATUS (temperature)
  - 0x1A2: MSR_IA32_TEMPERATURE_TARGET (TjMax)
  - 0x1AD: MSR_TURBO_RATIO_LIMIT (turbo ratios)
  - 0x606: MSR_RAPL_POWER_UNIT (power units)
  - 0x610: MSR_PKG_POWER_LIMIT (power limits)
  - 0x611: MSR_PKG_ENERGY_STATUS (package energy)
  - 0x614: MSR_PKG_POWER_INFO (TDP info)
  - 0x619: MSR_DRAM_ENERGY_STATUS (DRAM energy)
  - 0x639: MSR_PP0_ENERGY_STATUS (core energy)
  - 0x641: MSR_PP1_ENERGY_STATUS (graphics energy)

[2026-01-23 - Buffered I/O with METHOD_BUFFERED]
Reason:
  - Simpler than Direct I/O or Neither I/O
  - Kernel copies data to/from user buffers
  - Safe for small structures (<4KB)

Impact:
  - Both input and output use systemBuffer (shared buffer)
  - No need for MDLs or direct memory mapping
  - IO_STACK_LOCATION contains buffer lengths

Pattern:
  PHALFAX_XXX_REQUEST request = (PHALFAX_XXX_REQUEST)systemBuffer;
  PHALFAX_XXX_RESPONSE response = (PHALFAX_XXX_RESPONSE)systemBuffer;
  // Process request, fill response
  Irp->IoStatus.Information = sizeof(HALFAX_XXX_RESPONSE);
  IoCompleteRequest(Irp, IO_NO_INCREMENT);
